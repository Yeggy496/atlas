# OptiDay v0.2.5 · 先取得可行方案，再继续优化

## 部署后验收发现

公开网站v0.2.4已正确启用DeepSeek。用户输入框中没有“替换示例”前言的原文，在已有示例和重复识别两种情况下分别耗时19.50秒、9.36秒，均得到47活动、23约束，未重复增加任务；第二次一次识别通过。未审核的求解请求返回409，符合审核门槛。

但这次实际识别出的模型在Render单线程、30秒求解时限下返回UNKNOWN，尚未找到可行结果，也没有证明无解。因此本次验收未被记录为“全部成功”。本地同一模型只进行可行性求解能找到合法方案，说明值得先保住可行结果再优化。不同机器的耗时不能直接作为性能提升倍数。

## 改动

- 多目标求解先用最多三分之一、至多10秒的预算求一个满足全部硬约束的方案；随后将该方案作为CP-SAT提示，在同一总预算剩余时间内优化。
- 优化阶段若返回UNKNOWN，保留第一阶段真实找到的方案，并明确返回FEASIBLE；第一阶段的满足性OPTIMAL不被误报为原优化目标已最优。
- 回退仍执行独立结果校验，目标值仍按原有权重和处罚项计算；无法找到真实方案时仍返回UNKNOWN，真正无解时仍返回INFEASIBLE。
- 仅做可行性检查的冲突诊断和修复验证维持单次求解。没有放宽用户约束、改用模型生成排程或延长配置的求解总时限。

## 验证与限制

最终完整后端回归192项通过、1项需在线密钥的测试跳过。其中6项求解阶段回归覆盖：超时保留真实方案、原目标值与下界、共享时间预算、未找到方案仍UNKNOWN、真正无解、正常最优及47活动单线程案例，部分检查合并在同一用例中。匿名模型夹具位于 `backend/tests/fixtures/weekly_47.json`。11组产品流程和14组灰测浏览器流程也通过，包括本地保存、备份恢复、重排、审核和移动端操作，无页面异常。

本地同一份47活动模型已生成47项安排，独立校验0硬约束违反，另外22项案例条件核对通过。本版本仍需部署后在Render资源条件下复测，不能用本地成功代替线上成功。

这份已有示例的识别结果仍保留了“高数作业每天最多一次”。原输入仅要求分两次；审核时应检查是否继续保留原计划中的此类限制。自然语言语义准确率仍不能保证，审核步骤继续保留。
