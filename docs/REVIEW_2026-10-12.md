# ATLAS-Σ 当前功能、能力及提升分析报告

复核日期：2026-10-12。版本：桌面交付的 v0.1.4，加本次发布前修复。

对比基线：GitHub 原 main 提交 `4399b9a8a9176115d50016a75fe587e86097c3c7`，即此前部署的三场景版本。评估以源代码、实际运行及测试为准，交接文档中的“全部完成”“无已知 Bug”和完成率不作为结论。

## 1. 当前做到什么程度

**现在是一个可以运行、具有真实求解能力的小规模调度网站，已具备比赛演示的主要闭环。** 用户可以选择场景，输入文字或导入文件，检查结构化任务和约束，经 CP-SAT 求解后查看周日历、资源占用及安排解释；发生部分冲突时，可以应用经求解验证的放宽建议；可以保存最近的历史、重新优化并下载结果。

它已经超出最初三场景 Demo，但还不能称为“所有需求都很好地完成”。最主要的缺口是：页面上的资源及复杂任务配置不完整；新增并发场景的日历会遮挡事件；重排变化没有清晰的对比界面；默认自然语言解析仍是有限规则；公开服务没有用户数据隔离及长期保存机制。

对一个人、一个班、小型实验团队，当前方向合适。没有必要继续扩展更多场景或引入复杂基础设施，应优先把已有功能做顺畅。

## 2. 已实现功能及实际边界

| 功能 | 当前真实能力 | 使用边界 |
| --- | --- | --- |
| 五个场景 | 个人周计划、智能排课、实验室、会议室、生产工单 | 都共享模型和求解器；会议/生产输入界面较浅 |
| 个人计划 | 固定课程、睡眠、用餐、跑步、学习、截止作业、可选阅读 | 单周；睡眠示例固定 00:00–08:00；活动不能跨日 |
| 排课 | 教师/班级占用、候选教室、座位、类型、时段、连续时长及两活动连排 | 适合一个班；没有完整的学校基础数据录入界面 |
| 实验室 | 团队、实验室、设备数量、连续时长、前置关系与资源冲突 | 资源种类和需求数量可以在模型表达，页面不能全部维护 |
| 会议室 | 会议、参会人、候选房间、人数及房间类型限制 | 合法并发会议可能在日历上互相遮挡 |
| 生产工单 | 多工序分组、工序顺序、机台选择及完工截止 | 模板真实可解；页面不能完整新建/编辑工单链 |
| 自然语言 | `demo` 有限句式；OpenAI/DeepSeek 有真实服务端接口 | 本次没有使用真实密钥，不能据此确认线上模型已启用 |
| 审核及编辑 | 模型输出 Pydantic 校验、引用/约束检查；任务/约束可审核、增删改 | “审核”是显式确认，不是模型输出正确性的自动证明 |
| 文件导入 | CSV/XLSX 按模板读取活动；TXT/PDF 提取文字后进入解析和审核 | 不支持任意学校 Excel 自动识别；扫描 PDF 不支持 OCR |
| 优化偏好 | 高效、均衡、稳健，以及七个维度的自定义权重 | 指标是实际惩罚值，并非统一的百分制评分 |
| 结果可视化 | 周日历、24 小时切换、睡眠汇总、资源占用和每日负载 | 资源比例以整周 168 小时为分母，不能当作工作时间利用率 |
| 解释 | 按问题和结果生成规则事实；可选 LLM 润色，失败时保留事实 | 候选时段只是单活动筛选，未逐个复验全局可行性 |
| 冲突及修复 | 区分 INFEASIBLE/UNKNOWN；真实试删硬约束后求解验证 | 非最小冲突核心；只搜索有限的单条放宽，不保证总能修好 |
| 重新优化 | 可携带上次安排；稳健及修复流程使用稳定性惩罚 | 高效/均衡默认 stability=0，普通重排可能改变较多活动 |
| 方案对比 | `/api/compare` 可返回保留、移动、新增、移除及稳定率 | 尚无前端入口；网页不能完整展示前后变化 |
| 历史 | SQLite 保存，网页可恢复最近 12 条完整问题与结果 | 匿名全站共享；没有个人工作区或账号隔离 |
| 导出 | JSON、完整中文 XLSX（三个工作表）、可解析 PDF 摘要 | PDF 不支持中文字体，中文会显示问号，中文交付使用 Excel |

模型范围是 7 天 × 每天 48 个半小时槽；输入上限为 100 活动、50 资源、200 显式约束。**这些是限制值，不能当作已完成最大规模性能验证。** 当前软约束只有时间窗口偏好；每日上限表示活动次数，而非总小时。

| 方面 | 之前 | 四天后 |

| 调整证据 | changed 统计 | 增加完整对比 API；修复强制较高稳定性权重 |
| 交付能力 | 日历和 JSON 下载 | 新增中文 Excel 和 PDF 摘要 |
| 异常表达 | 基础冲突诊断 | 明确区分未证明无解的超时与已证明无解 |
| 复现及接力 | 基础测试、启动说明 | 更多后端测试、基准脚本、快照工具、提交前构建检查 |
| 部署包装 | 前端 dist 随源码提交 | 增加后端内置前端兜底构建副本 |

值得单独说明的一项变化：旧版高效/均衡模式原有稳定性权重，新版将它们改为 0。因此“增加了稳定性功能”不等于所有重新优化都更稳定；当前要保留旧安排，应使用稳健模式或适当的自定义稳定性权重。

真实 LLM 解析接口在旧版已经存在。本次增加的是连接配置、解释和验证路径，不能把“从无 AI 到有 AI”作为四天提升的描述。正式网站的排程结果仍来自 CP-SAT；`schedule_directly()` 只供比较实验使用。

## 4. 本次实际验证

验证环境：Windows、Python 3.12.14、实际安装的 OR-Tools、生产前端构建、FastAPI 同源服务；默认 `LLM_PROVIDER=demo`。浏览器验收使用 headless Chromium，覆盖桌面及 390px 手机宽度。

### 后端与部署检查

- 初次使用全新数据库时，79 项通过、5 项失败、1 项跳过。失败均来自导出测试未触发应用 lifespan，已有数据库掩盖了测试初始化缺口；生产服务器正常启动会创建表。
- 修复测试生命周期及本次发现的问题后，在另一全新数据库进行最终全量复测：**90 passed、1 skipped，耗时 95.88 秒**。跳过的是显式启用才运行的真实模型集成测试；另有一条 TestClient 依赖弃用提示。结构化记录见同目录 `review-verification-20261012.json`。
- TypeScript 检查和 Vite 生产构建通过。最终 JS 约 288.71 KB，gzip 约 89.23 KB。
- Render 官方 CLI 对修复后的 `render.yaml` 返回 `valid: true`。这是配置验证，不表示线上已经部署该版本。
- `frontend/dist` 与 `backend/app/webapp` 构建副本逐文件哈希一致。

### 五个场景的网页求解样例

以下为本地单次浏览器验收，求解时限 4 秒、4 个 worker；同机另有测试运行。它们是功能验证，不能作为服务器响应时间承诺或算法普适性证明。

| 场景 | 活动 | 资源 | 显式约束 | 状态 | 求解器耗时 | 独立校验硬违反 |
| --- | ---: | ---: | ---: | --- | ---: | ---: |
| 个人周计划 | 35 | 1 | 11 | FEASIBLE | 4.014s | 0 |
| 智能排课 | 11 | 6 | 5 | FEASIBLE | 4.010s | 0 |
| 实验室 | 6 | 6 | 4 | OPTIMAL | 1.225s | 0 |
| 会议室 | 6 | 5 | 4 | OPTIMAL | 0.471s | 0 |
| 生产工单 | 9 | 4 | 4 | OPTIMAL | 0.581s | 0 |

FEASIBLE 表示找到合法方案，但未在时限内证明目标最优；OPTIMAL 只表示对当前建模和目标证明最优。显示的耗时来自求解器，不含网络、页面加载及无解后的诊断耗时。

### 网页闭环验收

13 组流程通过：个人示例；TXT 导入→识别→强制审核→临时会议求解；自定义权重应用与恢复预设；资源及安排解释；三种结果下载；历史恢复；其余四场景求解；整单删除；无解→已验证修复→合法计划；桌面/手机布局。下载的 Excel/PDF 实际解析成功，JSON 与屏幕结果一致；浏览器无页面异常或控制台错误。

详细证据：`review-browser-evidence-20261012.json`。另有导入、边界和模型失败路径等自动测试；并非本轮每种文件都通过网页逐项导入。

### 没有证明的事项

本次没有进行付费模型在线调用、最大规模压测、长时间多人使用测试。仓库既有 `benchmark_results.md` 明确标注 `provider=demo`，其中 LLM 行是离线代理，不能当作真实模型对比结果。交接方记录的真实 DeepSeek 耗时本次未复验。

## 5. 本次发布前修复，区别于四天新增功能

桌面原文件夹保持原样；修复在 GitHub 工作副本中完成。

1. 修正 `render.yaml` 缩进，使 Render 可以解析部署配置。
2. 修复整张生产工单删除只删最后一步的状态问题；关联约束随所有步骤删除。
3. 修复权重恢复预设仍提交旧值、切换场景残留旧权重；恢复历史时显示该结果实际权重。
4. 前后端在 Repair 中保留自定义权重，同时仍启用修复流程的稳定性项。
5. 独立诊断接口增加与正式求解相同的审核门槛，并携带用户权重。
6. 修正解释：候选数量不再声称“全局可行/唯一”；不解释其他日期的偏好；正确描述最小间隔与紧邻关系。
7. 修复导出遗漏实际选中教室/机台及资源数量；Excel 每日负载排除睡眠，与页面口径一致。
8. 补上会议和生产的冲突示例，避免按钮引用旧场景任务造成服务器错误；已修改活动不适用示例时返回友好错误。
9. 修正导出测试的应用初始化，并为审核、权重、解释、导出、新场景冲突增加回归测试。
10. 重新构建前端、同步兜底产物，并给历史交接文档加上本次复核入口。

## 6. 接下来最值得提升什么

| 优先级 | 建议 | 用户能获得的变化 | 验收方式 |
| --- | --- | --- | --- |
| 第一优先 | 并发事件自动分列，或按资源展示时间线 | 会议/生产的合法并发任务都能看见、点击 | 同时安排两场会议/两台机床，事件不遮挡 |
| 第一优先 | 补齐资源管理及活动资源字段 | 用户可以从零输入自己的教室/教师/设备，完整设置容量、类型和多个资源 | 不使用示例，建立一个班的课表并验证教室限制 |
| 第一优先 | 将 `/compare` 接入网页，加“保留原安排”开关 | 看见哪些任务移动、移动多少，并选择保留程度 | 插入临时会议，显示移动前后、保留数和新任务 |
| 第一优先 | 选择实际周日期，保存个人工作区草稿 | 下周仍能使用；不必每次从示例重建 | 切换周、刷新、恢复草稿，日期和任务正确 |
| 后续 | 用真实模型做小型验收集，增加解析前后变更摘要 | 自然语言理解更灵活，用户能发现遗漏或误改 | 十几条自己的输入，核对实体、硬软约束和截止日期 |
| 后续 | 统一文本提取与解析长度限制 | 长 TXT/PDF 不会提取成功后才遇到 422 | 当前提取上限 20,000 字，解析上限 4,000 字；明确分段或限制提示 |
| 后续 | 完整工单及工序编辑 | 生产场景可用于用户自己的工单，而非主要依赖模板 | 新建/调整/删除整个工单，工序关系合法 |
| 后续 | 轻量历史隔离、访问限制及调用额度 | 公开使用时日程不混在一起，模型费用可控 | 两个浏览器会话不互见历史，匿名请求不能无限消耗模型 |
| 后续 | 持久化与部署稳定性 | 部署/重启后不丢历史，访问体验稳定 | 实际重启后历史仍在；分别记录冷启动与求解耗时 |
| 最后 | 中文 PDF、更多评测实例、展示细节 | 交付体验和比赛证据更完整 | 中文可读导出；多密度、多种子、真实模型对比 |

若只剩两天，建议第一天完成并发显示、换周和核心资源输入；第二天完成重排对比、真实模型验收及三个主场景完整演示。暂缓新增场景、账号权限系统或复杂部署架构。

## 7. GitHub、接力及线上状态

本次发布内容是应用源码、锁文件、测试、脚本、演示数据、验证过的前端产物及本报告。排除 `.env`、实际 SQLite 数据库、依赖缓存、本地快照及原始审计附件。拟发布内容经过常见密钥模式检查；`.env.example` 只包含空密钥配置。

接力开发应以仓库 `main` 为准；后续开发者克隆仓库、安装依赖、阅读本报告和 `README.md` 即可。虚拟环境和 `node_modules` 不应从另一台电脑直接搬运。前端改动需要重新打包，并提交 `frontend/dist`；仅修改 TSX 后推送不会改变 Render 服务使用的构建文件。后端兜底副本也需要同步。

原公共网址为 `https://atlas-ptbu.onrender.com`。复核时 Render 在线提交仍是上述旧版 `4399b9a`。GitHub 推送与 Render 上线是两个动作，最终线上状态见本次回复或发布记录。本次没有购买域名或升级服务器；仓库配置仍为免费实例、`/tmp/atlas.db`。免费服务的休眠和临时数据库特性不会因源码更新自动消失。

对于比赛展示，最可信的表述是：**共享约束模型 + 真实 CP-SAT 求解 + 独立校验 + 经验证的修复建议，面向小规模真实调度。** 避免宣称任意自然语言理解、全局最小冲突核心、所有重排都最小扰动，或已经通过大规模多人验证。
